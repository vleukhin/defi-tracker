# ТЗ. Часть 6: Развертывание в облаке

**Версия:** 1.0 (30.07.2026)
Стек по ТЗ Часть 4 §1: **Vercel Hobby + Supabase Free = $0/мес.**

Шаги, помеченные **[вы]**, требуют входа в аккаунты — их выполняете вы.
Помеченные **[скрипт]** — запускаются командой из проекта.

---

## 0. Перед началом

- [ ] Свежая резервная копия локальных данных: `npm run data:export`
      (файл `backup-ГГГГ-ММ-ДД.json`, в репозиторий не попадает).
- [ ] Все коммиты отправлены на GitHub: `git push`.
- [ ] Под рукой ключи `ALCHEMY_API_KEY` и `COINGECKO_API_KEY` из `.env.local`
      — в облаке используются те же самые.

## 1. Проект Supabase **[вы]**

1. [supabase.com](https://supabase.com) → **New project**.
   - Регион: ближайший к вам (для Европы — `Central EU (Frankfurt)`).
   - **Пароль базы сохраните** — понадобится на шаге 2 и больше нигде не показывается.
2. Дождитесь создания (1–2 мин).
3. **Project Settings → API** — оттуда понадобятся три значения:
   - `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
   - `anon public` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `service_role` → `SUPABASE_SERVICE_ROLE_KEY` (**секрет**, только сервер)

> **Адрес — без хвостов.** Нужен базовый вид `https://<ref>.supabase.co`.
> Рядом на той же странице показаны REST- и GraphQL-адреса
> (`…/rest/v1/`, `…/graphql/v1`) — они **не подходят**: клиент дописывает
> свои пути сам, и лишний хвост дает ошибку
> `Invalid path specified in request URL`. Скрипты такой хвост срезают
> и предупреждают, а вот в переменных Vercel адрес должен быть сразу
> правильный.

## 2. Миграции в облачную базу **[вы]**

```bash
npx supabase login
npx supabase link --project-ref <ref-проекта>
npx supabase db push
```

`ref` — в адресе панели: `supabase.com/dashboard/project/<ref>`.
`db push` накатит все миграции: схему, RLS-политики, GRANT'ы, справочник
активов, модель портфеля, сделки.

Проверка: **Table Editor** — должны быть таблицы `wallets`, `trades`,
`manual_positions`, `portfolio_targets`, `protocol_positions`, `coin_prices`.

## 3. Настройки Auth **[вы]** — здесь легко ошибиться

**Authentication → Sign In / Providers → Email:**

| Настройка | Значение | Почему |
|---|---|---|
| **Enable Email provider** | **ВКЛ** | Выключение убивает и вход тоже — приложение станет недоступно |
| **Confirm email** | **ВЫКЛ** | Аккаунты создает админ, почта считается подтвержденной |

**Authentication → Sign In / Providers → внизу «Allow new users to sign up»: ВЫКЛ.**
Именно эта пара (провайдер включен, регистрация выключена) дает закрытый
контур: войти можно, зарегистрироваться самому — нет. Если выключить
провайдер целиком, вход вернет `email_provider_disabled`.

**Authentication → URL Configuration:**
- `Site URL`: адрес продакшена (например `https://defi-tracker.vercel.app`)
- `Redirect URLs`: добавьте `https://<ваш-домен>/**`

**Authentication → Emails → Reset Password** — замените ссылку на:

```
{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery
```

Стандартный шаблон Supabase не работает с cookie-сессиями `@supabase/ssr`:
ссылка восстановления пароля молча не сработает. Локальный аналог —
`supabase/templates/recovery.html`.

## 4. Vercel **[вы]**

1. [vercel.com](https://vercel.com) → **Add New → Project** → импорт
   репозитория `vleukhin/defi-tracker`.
2. Framework определится сам (Next.js), настройки сборки менять не нужно.
3. **Environment Variables** — восемь переменных для Production:

| Переменная | Значение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL из шага 1 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon public |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role (**секрет**) |
| `ALCHEMY_API_KEY` | из `.env.local` |
| `COINGECKO_API_KEY` | из `.env.local` |
| `CRON_SECRET` | случайная строка (**секрет**), см. шаг 4а |
| `TELEGRAM_BOT_TOKEN` | токен бота (**секрет**), см. шаг 4б |
| `TELEGRAM_BOT_USERNAME` | имя бота без «@», см. шаг 4б |

`ADMIN_EMAIL` / `ADMIN_PASSWORD` в Vercel **не нужны** — админ создается
скриптом с вашей машины (шаг 5).

4. **Deploy.** После деплоя вернитесь в Supabase и впишите полученный адрес
   в `Site URL` (шаг 3), если он тогда был неизвестен.

## 4а. `CRON_SECRET` — ежедневные снепшоты **[вы]**

Расписание лежит в `vercel.json` и подхватывается при деплое само:

```json
{ "crons": [{ "path": "/api/cron/snapshot", "schedule": "0 3 * * *" }] }
```

Роут работает под service-role и открыт в интернет, поэтому пускает только
по секрету: `Authorization: Bearer <CRON_SECRET>`. **Без переменной роут
отвечает 500, с неверным значением — 401**, и снепшоты просто не снимаются
(в Vercel → Cron Jobs это видно как красные запуски). Заголовок
`x-vercel-cron` сам по себе ничего не доказывает — подделать его тривиально.

1. Сгенерируйте значение:

   ```bash
   openssl rand -hex 32
   ```

2. Vercel → **Settings → Environment Variables** → `CRON_SECRET` = это
   значение, окружение **Production**. Vercel подставляет его в заголовок
   своих cron-запросов автоматически — вручную ничего вызывать не нужно.
3. **Передеплойте** (переменные подхватываются только новой сборкой).
4. Проверка вручную:

   ```bash
   curl -i https://<домен>/api/cron/snapshot                      # 401
   curl -i -H "Authorization: Bearer <CRON_SECRET>" \
     https://<домен>/api/cron/snapshot                            # 200 + JSON
   ```

**Про расписание.** `0 3 * * *` — 03:00 UTC (S3.1); календарный день снепшота
(`taken_on`) тоже считается по UTC, поэтому смены даты на границе не бывает.
На плане **Hobby доступен один запуск в сутки, и время выполняется с
разбросом примерно до часа** — снепшот может сняться в 03:00–04:00 UTC. Для
дневной точки истории это не важно. Повторный запуск за тот же день ничего не
дублирует: `UNIQUE (user_id, taken_on)` перезаписывает существующую точку —
поэтому ретрай безопасен, как и кнопка «Снепшот сейчас».

## 4б. Телеграм-бот — уведомления о health factor **[вы]**

Мониторинг HF ходит в сеть каждые 15 минут и пишет, когда health factor
уходит ниже порога, резко падает или восстанавливается. Расписание там же,
в `vercel.json`:

```json
{ "path": "/api/cron/health", "schedule": "*/15 * * * *" }
```

> **Нужен тариф Pro.** На Hobby cron ограничен одним запуском в сутки, и
> расписание чаще просто не примут. Мониторинг HF раз в сутки бессмысленен:
> ликвидация приходит быстрее. Это единственная причина, по которой проект
> перестал укладываться в $0/мес.

1. **Создайте бота.** В телеграме напишите [@BotFather](https://t.me/BotFather),
   команда `/newbot`, придумайте имя и username. В ответ придёт токен вида
   `123456789:AA...`.
2. **Vercel → Settings → Environment Variables** (окружение **Production**):
   `TELEGRAM_BOT_TOKEN` = токен, `TELEGRAM_BOT_USERNAME` = username без «@».
   Если привязку проверяют на превью-URL из pull request, отметьте обе
   переменные и для окружения **Preview** — иначе на превью бота нет.
   Пока токен не задан, карточка «Уведомления» показывает «бот не настроен»
   вместо кнопки «Подключить»: код привязки в таком окружении разобрать нечем.
3. **Убедитесь, что вебхука нет.** Привязка чатов читает `getUpdates`, а он
   несовместим с вебхуком — телеграм ответит 409:

   ```bash
   curl "https://api.telegram.org/bot<ТОКЕН>/deleteWebhook"
   ```

4. **Передеплойте** и подключите свой чат: «Настройки» → «Уведомления» →
   «Подключить» → отправьте боту `/start <код>` → «Проверить». Кнопка
   «Отправить тестовое» подтверждает, что сообщения доходят.

**Что приходит.** Уход в более низкую зону HF и возврат обратно, повторные
напоминания, пока HF ниже порога (раз в 6 часов; на экстренном уровне — раз
в час), резкое падение на 10% и более, а также сообщение, если HF перестал
читаться дольше 6 часов: молчание не должно быть неотличимо от «всё хорошо».
Каждый кошелёк и каждая сеть отслеживаются отдельно — ликвидация приходит
к конкретной позиции.

**Если сообщения не приходят.** Смотреть Vercel → **Cron Jobs** (логи
запусков `/api/cron/health`) и таблицу `notification_log` в Supabase: там
лежит текст каждой попытки и ошибка. Заблокированный бот гасит канал сам —
в «Настройках» это видно строкой с причиной.

## 5. Админ и данные **[скрипт]**

Создайте `.env.production.local` в корне проекта (файл игнорируется git):

```
NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon>
SUPABASE_SERVICE_ROLE_KEY=<service_role>
ADMIN_EMAIL=<ваш email>
ADMIN_PASSWORD=<надежный пароль, минимум 8 символов>
```

Затем:

```bash
npm run seed:admin:prod
npm run data:import:prod -- --file backup-ГГГГ-ММ-ДД.json
```

Первая команда заводит администратора, вторая переносит кошельки, ручные
записи, цели и сделки. Импорт не задваивает: если данные уже есть, таблица
пропускается (перезаписать — флаг `--replace`).

**Пароль в продакшене задайте другой, чем локальный.** Локальный
`admin-local-1` — учебный.

## 7. Что помнить дальше

- **Vercel Pro ($20/мес) — обязателен с Фазы 6.** Мониторинг HF требует
  запусков каждые 15 минут, а Hobby даёт один в сутки. До этого проект
  укладывался в $0/мес; если уведомления не нужны, достаточно убрать
  `/api/cron/health` из `vercel.json` и вернуться на Hobby.
- **Supabase Free засыпает после 7 дней простоя.** Ежедневный cron из
  Фазы 3 будет держать проект живым сам по себе.
- **Cron для снепшотов** настроен (шаг 4а): `vercel.json` + роут
  `/api/cron/snapshot` под `CRON_SECRET`. Если история перестала
  пополняться — смотреть Vercel → **Cron Jobs** (там же логи запусков):
  чаще всего это истекший или потерянный при ротации `CRON_SECRET`.
- **Cron мониторинга HF** (шаг 4б): `/api/cron/health` под тем же секретом.
  Молчащие уведомления проверяются там же плюс `notification_log`.
- **Резервные копии.** `npm run data:export:prod` выгружает облачные данные
  в том же формате. На Supabase Free автоматических бэкапов нет — выгружать
  раз в месяц стоит.
- **Ротация ключей.** Если `service_role` куда-то утек — перевыпуск в
  Project Settings → API, затем обновить переменную в Vercel.
