# ТЗ. Часть 2: Фаза 1 (MVP) — «Компактный трекер портфеля»

**Версия:** 2.0 (30.07.2026)
Документ самодостаточен: разработчик может реализовать Фазу 1, не читая остальные части (архитектурные детали — в [04-arhitektura.md](04-arhitektura.md)).

---

## 1. Цель фазы

Пользователь добавляет свои EVM-адреса, приложение читает залог BTC и ETH на лендинг-маркетах (Aave v3, четыре сети), пользователь вносит проинвестированные стейблкоины и при необходимости корректирует количества вручную. На выходе — одна компактная таблица из трех строк: количество, стоимость, цена, доля, цель, отклонение и **количество монет к ребалансировке**.

**Учет портфеля не зависит от долгов.** Заемные средства не вычитаются из категорий и не влияют на проценты — они появятся отдельным контуром в Фазе 4.

**В MVP нет:** долга и health factor, GMX/LP-позиций, сделок и средней цены, снепшотов, истории, экспорта.

## 2. Состав MVP

1. Вход (закрытая регистрация — аккаунты создает администратор), изоляция данных.
2. Управление кошельками (read-only адреса).
3. Чтение залога (supplied) Aave v3 на 4 сетях: активы категорий BTC и ETH.
4. Ручные записи: подписанные суммы стейблов и корректировки BTC/ETH.
5. Цены из CoinGecko через общий серверный кэш.
6. Целевые проценты по трем категориям.
7. Компактная таблица портфеля с отклонениями и количеством к ребалансировке.

## 2а. Модель портфеля (ядро фазы)

Портфель — **всегда три фиксированные категории**: `BTC`, `ETH`, `Stablecoins`. Произвольных корзин, переопределений и маппинга активов нет.

Источники количества:

| Категория | Источник |
|---|---|
| BTC | Залог Aave v3 (WBTC, cbBTC, tBTC — что доступно в сети) + ручные корректировки в BTC |
| ETH | Залог Aave v3 (WETH, wstETH, weETH, rETH, cbETH и др.) + ручные корректировки в ETH |
| Stablecoins | Только ручные подписанные записи в USD («GMX пул» 15 000, «Aave USDC» 20 000) |

Цены: BTC — CoinGecko `bitcoin`, ETH — `ethereum`, стейблы — фиксированно $1.00.

**Оценка LST и wrapped-активов.** Каждый актив залога оценивается по своей цене (1 wstETH ≈ 1.2 ETH — считать его за 1 ETH нельзя). Поэтому:

```
стоимость категории = Σ(количество актива × его собственная цена) + Σ(ручные записи в USD)
количество категории = стоимость категории / цена категории     // BTC- или ETH-эквивалент
```

Формулы расчета (проверены на реальной таблице пользователя):

```
итого            = Σ стоимость категории
доля, %          = стоимость категории / итого × 100
отклонение, п.п. = доля − цель
к ребалансировке = (цель/100 × итого − стоимость категории) / цена категории
```

`к ребалансировке` — **в единицах категории** (BTC, ETH или USD для стейблов): отрицательное значение = продать, положительное = купить. При нулевом итоге доли и количества к ребалансировке равны нулю; без заданной цели отклонение и количество к ребалансировке не показываются.

Контрольный пример (должен воспроизводиться тестами): BTC 1.2611 по $64 310 = $81 098; ETH 16.9188 по $1 912 = $32 355; стейблы 39 548 по $1 = $39 548; итого $153 001; доли 53.00 / 21.15 / 25.85%; цели 50 / 20 / 30%; отклонения +3.00 / +1.15 / −4.15 п.п.; к ребалансировке −0.071486 BTC / −0.917713 ETH / +6 352 USD.

## 3. User stories и критерии приемки

### S1.1. Вход и управление пользователями
*Как пользователь, я вхожу по email и паролю; аккаунты создает администратор.*

- [ ] **Публичной регистрации нет** (signup отключен на уровне Supabase); подтверждение email отключено.
- [ ] Администратор сидируется идемпотентной командой `npm run seed:admin` из переменных окружения `ADMIN_EMAIL` / `ADMIN_PASSWORD` (роль в `app_metadata.role`, задается только через service-role API).
- [ ] Администратор создает и удаляет пользователей в разделе «Настройки» (email + пароль, минимум 8 символов); удаление пользователя каскадно удаляет его данные; удалить собственный аккаунт нельзя.
- [ ] Пароли хэшируются средствами Supabase Auth; сброс пароля по ссылке на email.
- [ ] Rate-limit на попытки входа; сессии HttpOnly + SameSite; только HTTPS.
- [ ] Ни один пользователь не может получить данные другого ни через один API-роут — покрыто автотестом (RLS-политики, см. Часть 4 §5); админ-роуты `/api/admin/*` возвращают 403 без роли администратора.

### S1.2. Управление кошельками
*Как пользователь, я добавляю один или несколько EVM-адресов (read-only), чтобы залог подтягивался автоматически.*

- [ ] Добавление адреса: валидация формата и EIP-55 checksum; опциональная метка («Основной», «Ledger»).
- [ ] Один адрес автоматически отслеживается на всех 4 сетях; отключение отдельных сетей не требуется в MVP.
- [ ] Удаление кошелька убирает его залог из портфеля.
- [ ] **Нигде в UI нет полей, упоминаний или запросов приватных ключей и сид-фраз.** Явный текст при добавлении: «Только просмотр. Приложение не может распоряжаться средствами».
- [ ] Резолвинг ENS-имен — nice-to-have, не обязателен.

### S1.3. Чтение залога Aave v3
*Как пользователь, я вижу количество BTC и ETH, лежащее у меня в залоге, без ручного ввода.*

- [ ] Читается **залог (supplied)** Aave v3 по каждому адресу на Ethereum, Arbitrum, Base, Optimism: балансы aToken'ов через `balanceOf` батчем в Multicall3 (`allowFailure: true`). Баланс aToken уже включает начисленные проценты — пересчет через liquidity index не нужен.
- [ ] Адреса aToken'ов берутся из `@bgd-labs/aave-address-book`, не прописываются руками.
- [ ] Покрываются активы категории BTC (WBTC, cbBTC, tBTC — где есть в сети) и ETH (WETH, wstETH, weETH, rETH, cbETH и другие, доступные в сети).
- [ ] Заемные средства (debt-токены) в этой фазе **не читаются и не влияют** на портфель.
- [ ] Обновление: по кнопке «Обновить» (debounce 60 с на кошелек) и автоматически не чаще раза в 15 минут при открытом дашборде.
- [ ] Отказ RPC одной сети изолирован: показываются последние известные данные с бейджем «данные устарели», дашборд не пустеет; упавший вызов трактуется как «неизвестно», не как ноль.
- [ ] Decimals берутся из справочника/контракта, никогда не предполагаются равными 18 (WBTC = 8). Сырые значения — bigint, перевод в десятичную строку только на границе отображения.

### S1.4. Ручные записи
*Как пользователь, я вношу проинвестированные стейблы и корректирую количества BTC/ETH.*

- [ ] Стейблы: несколько записей «подпись + сумма в USD» (например «GMX пул» 15 000, «Aave USDC» 20 000); сумма по категории считается автоматически.
- [ ] BTC и ETH: записи-корректировки в единицах монеты — для средств вне лендинга (биржа, холодный кошелек); прибавляются к залогу.
- [ ] Записи создаются, редактируются и удаляются; подпись до 60 символов, сумма больше нуля.
- [ ] В таблице портфеля видно разделение «из залога / внесено вручную» по каждой категории.

### S1.5. Цены
*Как пользователь, я вижу стоимость портфеля в USD по актуальным ценам.*

- [ ] Цена категории: BTC — CoinGecko id `bitcoin`, ETH — `ethereum`, стейблы — фиксированно $1.00.
- [ ] Активы залога оцениваются по **своим** ценам (wstETH, weETH, rETH и т.п. — не приравниваются к 1 ETH); количество категории выводится как стоимость / цена категории (BTC- или ETH-эквивалент).
- [ ] Запросы только с сервера, через общий кэш с TTL 5 минут; token-bucket лимитер 25 запросов/мин; при сбое CoinGecko отдается последняя известная цена с пометкой устаревания.
- [ ] На дашборде видна метка свежести цен и данных залога.
- [ ] Атрибуция «Price data by CoinGecko» со ссылкой — в футере.

### S1.6. Целевые проценты
*Как пользователь, я задаю целевые проценты по трем категориям, чтобы измерять отклонение.*

- [ ] Три поля: BTC, ETH, Stablecoins (0–100, шаг 0.5). Пустое поле — цель не задана.
- [ ] Живой индикатор суммы: 100% — норма, иначе предупреждение «Сумма: X%» — **предупреждение, не блокировка**.
- [ ] Цели сохраняются на пользователя и применяются к расчету немедленно.

### S1.7. Компактная таблица портфеля
*Как пользователь, я вижу всю картину в одной небольшой таблице.*

- [ ] Строки: BTC, ETH, Stablecoins — **всегда все три**, даже при нулевых количествах.
- [ ] Столбцы: Количество · Стоимость USD · Цена · Доля % · Цель % · Отклонение п.п. · К ребалансировке. Итоговая стоимость портфеля — под таблицей и/или в шапке.
- [ ] Формулы — по §2а; `к ребалансировке` показывается в единицах категории со знаком (отрицательное — продать).
- [ ] Форматирование: количество BTC/ETH — до 4 знаков в таблице (полное значение доступно при наведении/раскрытии), к ребалансировке — до 6 знаков; USD — без копеек с пробелом-разделителем тысяч ($81 098); проценты — 2 знака.
- [ ] Отклонения за пределами ±5 п.п. визуально выделены; цвет не единственный признак (знак/стрелка обязательны).
- [ ] Строка раскрывается в состав: активы залога (символ, сеть, количество, цена, стоимость) и ручные записи.
- [ ] Дашборд загружается < 2 с на кэшированных данных; полностью удобен на экране 375 px (таблица превращается в стек карточек, без горизонтальной прокрутки страницы).
- [ ] Пустые состояния: нет кошельков → CTA на добавление; нет данных → понятное объяснение, а не пустая таблица.

## 4. Out of scope Фазы 1 (явно)

- Долг, health factor, любые заемные средства — Фаза 4 (отдельный контур, портфель не затрагивает).
- GMX GM-пулы и Uniswap v3 LP — Фаза 5.
- Сделки, средняя цена, P/L — Фаза 2.
- Снепшоты и история — Фаза 3.
- CSV-экспорт, метки/фильтры по кошелькам, алерты, 2FA — Фаза 6.
- Произвольные корзины и категории кроме трех; альткоины; разбор истории транзакций; подпись транзакций; не-EVM сети; NFT; валюты кроме USD.
- Чтение свободных ERC-20 балансов кошелька: код читателя сохранен для Фазы 5, но в расчете портфеля не участвует (свободные монеты вносятся ручными записями).

## 5. Определение готовности фазы

- Все критерии приемки S1.1–S1.7 выполнены.
- Контрольный пример из §2а воспроизводится юнит-тестами (доли, отклонения, количество к ребалансировке).
- Автотест изоляции данных проходит (два пользователя не видят данных друг друга); админ-роуты возвращают 403 без роли.
- Реальный залог в Aave (несколько сетей) сходится по количествам с интерфейсом Aave.
- Расход API за неделю тестирования ≤ 25% лимитов бесплатных тарифов.
- Путь «вход → адрес → записи стейблов → цели → отклонения» проходится за ≤ 10 минут.
